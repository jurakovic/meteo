
# Internals

### Overview

Two main folders:

[`src`](./src)
- contains source files for site build
- no particular framework is used, only vanilla HTML, CSS, and JavaScript
	- all build *magic* is done in [`build.sh`](./src/build.sh) and [`build.ps1`](./src/build.ps1) scripts

[`docs`](./docs)
- contains build output
- source for GitHub Pages publish

### Commands

#### Run from src

```bash
docker run -d -p 8080:80 --name meteo -v "$(pwd)/src:/usr/share/nginx/html" nginx
```

Open <http://localhost:8080>

#### Run from docs (built site)

The build rewrites paths for GitHub Pages (`/meteo/...`), so mount `docs/` under the same subpath:

```bash
docker run -d -p 8081:80 --name meteo-docs -v "$(pwd)/docs:/usr/share/nginx/html/meteo" nginx
```

Open <http://localhost:8081/meteo/>

#### Minify JS and CSS

> [`terser`](https://www.npmjs.com/package/terser), [`clean-css-cli`](https://www.npmjs.com/package/clean-css-cli)

```bash
docker run -it --rm --entrypoint sh -v "$(pwd):/meteo" node:22-alpine

# inside container
npm install terser -g
npm install clean-css-cli -g
cd meteo/src/_assets
terser js/main.js --compress --mangle -o js/main.min.js --format max_line_len=140
terser js/maps.js --compress --mangle -o js/maps.min.js --format max_line_len=140
terser js/popout.js --compress --mangle -o js/popout.min.js --format max_line_len=140
cleancss --format 'wrapAt:140' -o css/styles.min.css css/styles.css
```

#### Build

```bash
cd src
./build.sh
```

`build.sh` runs `unix2dos` over all four minified assets before calling `build.ps1`, and over the built `.html` afterwards. The first pass is not cosmetic: terser and clean-css write LF, and `Prepend-Tabs` splits on CRLF, so an asset left at LF is one single line to it and reaches `docs/` with only its first line indented. The list has to name every asset — `maps.min.js` and `popout.min.js` were missing from it, which is why their inlined bodies used to sit unindented in the built page.

`build.ps1` produces `docs/` from `src/` by processing every `.html` file (except `_components/`):

1. inlines the minified assets (`styles.min.css`, `main.min.js`, `maps.min.js`, `popout.min.js`) in place of their `<link>`/`<script>` tags, each line indented by `Prepend-Tabs`
2. injects `_components/*.c.html` (seo, gtag, links) at their placeholders
3. rewrites dev paths to GitHub Pages paths (`href="/customize/index.html` → `/meteo/customize/`, `href="/"` → `/meteo/"`, image paths, the extras stub's `url=`)
4. strips HTML comments, trims trailing whitespace, collapses blank lines

### Maps catalog

The landing page ([`src/index.html`](./src/index.html)) is plain static HTML and does not load `maps.js`. The customize page ([`src/customize/index.html`](./src/customize/index.html)) renders its maps client-side by [`maps.js`](./src/_assets/js/maps.js) from a single catalog (`MAP_CATALOG`) into `<tbody data-maps>`. `maps.js` is loaded before `main.js` (both `defer`) and renders immediately when the DOM is already parsed (dev, deferred external script) or on `DOMContentLoaded` otherwise (the docs build inlines it into `<head>`, where `defer` does not apply) — either way before the wiring in `main.js` runs, so it sees the finished DOM. The pop-out widgets and snap columns (below) live in [`popout.js`](./src/_assets/js/popout.js), loaded before `maps.js`: the render calls into it (the title bar buttons, the columns reset with the tbody), so it has to be there at parse time, while it only reaches back into `maps.js` (`el()`, the catalog, the preferences) and `main.js` (`dlog()`, the fullscreen) from functions called later. The restore of the remembered arrangement is registered on `DOMContentLoaded` at the end of `maps.js`, after its own render listener, so the order holds in the docs build too, where both are inline in `<head>` and wait for that event. All three are classic scripts sharing the global scope; nothing is exported. `src/extras/index.html` is only a redirect stub to the customize page (kept for old bookmarks).

Note: the landing page's maps are duplicated in the catalog — a URL or layout change there must be applied in both places.

#### Map descriptors

Every map is one object with `id`, `category` (radar/satelit/munje/… — shown as a glyph in the picker, see `CATEGORY_GLYPHS`), `name` (shown both in the title bar and in the settings picker), `titleHref`, optional `maxWidth`/`aspect`, `links`, an optional `backdrop` (a `data:` URL standing in for the image a letterboxed widget's `.po-backdrop` would otherwise take from the map — only a `video` needs one, having no image at all; it is scaled to cover and blurred by 14px, which leaves colour and coarse shape and nothing else, so one frame at 64×43 and JPEG q60 is indistinguishable from the full one and costs 1.8 kB), and a `type`:

| type | notes |
|---|---|
| `slideshow` | `slides` is an array of image URLs, or of `{ title, img, aspect }` objects when each slide has its own title bar (a titled slide's `.slide.active` and its `.placeholder` are both `width: 100%`, so the box comes from the slideshow above rather than from the image below: a slide is a flex item and was sized by its content, and an image that fails to load is 0×0 — `img` carries `max-width` and no `width` — so the slide fell in to the width of the words in its title bar and a map whose source was down became a small tile. An untitled slideshow never had this, its container being the `.placeholder` itself and carrying the `aspect-ratio`, which is why a failed ESSL or ESTOFEX left a full-size box where ČHMÚ and meteoblue did not. The `.placeholder`'s own `aspect-ratio` and `max-width` then say how tall and how wide the map is with no image to ask, and its `img` is centred by `margin-inline: auto`, the shrink-to-fit slide having been centred itself) (`title.text` may be omitted to inherit the map's `name` — useful when only the `href` differs per slide); `startSlide` (1-based) is eager, the rest lazy-load unless `eagerSlides`; `dynamicWidth` resizes the container to the active slide, and only works on titled slideshows — `updateSlideshowWidth()` reads the active slide's `.placeholder` wrapper, which untitled slides do not have |
| `image` | single `img`, optional `alt` |
| `video` | mp4 `src`; `videoClass` picks the aspect wrapper (`vid1`/`vid2`) |
| `iframe` | interactive map with HR/EU zoom switch, overlay gate and fullscreen; `frameId` plus `srcHr`/`srcEu` and the four `zoom*` marker strings consumed by `setIframeSrc()` in `main.js` |
| `iframe-basic` | plain lazy iframe (`src`), no overlay/zoom |

The repeated per-map link rows come from shared groups (`RADAR_HR_LINKS`, `SAT_EU_LINKS`, …); `except(group, 'Name')` implements the "same set minus the map itself" pattern.

#### Presets and preferences

`DEFAULT_MAPS` holds the default order (mirroring the landing page); `MAP_PRESETS` lists the built-in presets, each carrying its own `maps` id list so resolving one is a plain lookup (`zadano` is the default set — displayed as *Osnovno*, but the id stays `zadano` because it is written into saved preferences and shared links; `vise` is the former extras set, `sve` the whole catalog, `nista` none). The "Karte" button opens the settings panel — a fixed dialog (`#mapSettings`, at body level in the markup, `z-index` over everything: the page, the columns, a fullscreen map, the widgets) rather than a block in the page, so it can be reached from any state of the page; not modal, since the arrangement is changed behind it while it is open (a map popped out, a pane snapped — see below), though the page holds still under it (`body.ms-open` locks its scroll — with the gutter of the scrollbar the page had kept, `html.ms-gutter` → `scrollbar-gutter: stable`, set by `setMapSettingsVisible()` only when there was one, so nothing centred in the page shifts — `clientWidth` counts the kept gutter, so `viewportWidth()` in `popout.js` takes `viewportGutter` off it meanwhile, or the columns would be laid out into the gutter; the columns are laid out again in case the viewport did change); its header stays and the `.ms-body` under it scrolls, with `overscroll-behavior: contain` so the wheel stops at its end instead of going on to the page, and, on the desktop, a classic styled scrollbar in a stable gutter, since the overlay kind shows an empty track until hovered and lies over the row handles (the picker's drag auto-scroll scrolls this body, by its edges) — the styling and the gutter are inside the desktop media query, so below the breakpoint the native overlay scrollbar stands, there being no hover to miss it and no row handles for it to cover, and an overlay scrollbar is what everything else on a touch screen has. Its `display: flex` (header over scrolling body) would beat the `hidden` attribute, so the CSS restates `display: none` for `[hidden]` — without it the shut dialog stands as an empty bordered box. Shut by its *Zatvori*, the button (`.ms-toggle`), Escape, `K`, which also opens it, or a `pointerdown` anywhere outside it — with what was edited in it dropped, as it is rebuilt from what is stored on the next open; the button and the tab are excepted, since their click would open it right back (`keydown` on `document`, not from a text field: the name and rename editors have an Escape of their own). Where the page that carries the button is gone — hidden behind full-width columns (`body.snap-full`) or on the board (`body.dashboard`), the two states the CSS shows it in — a fixed `.ms-tab` hangs from the top edge of the viewport to open it, in the site's orange on white rather than the bar grey of the furniture: where it shows it is the only way to the dialog. It hangs over the board the whole time it is shown, and the board is the maps, so it is faint (`opacity: 0.55`) until it is wanted — the widgets under it are not read through a strip of orange — and lit by the pointer or by `body.ms-open`, the dialog it opens being up, where it is the button that is pressed in. Not under a fullscreen map (`body.fs-lock`), though the page is just as far out of reach there: that map is one thing to look at and has its own ways out — the bar that stays on screen, Escape, the double-click — so a tab over it is chrome in front of the one view that asked for none, and it arrived on the phone too, `fs-lock` being the only one of the three a touch screen can reach at all. For the same reason it carries the glyph cluster a widget's title bar does (`buildMsTabCluster()`), the common moves being otherwise a dialog away: `[R]` reloads every widget's map, `[G]` and `[S]` are the board's two grid switches, each glyph the letter of the key that does the same thing and titled with it. They are `<a>` without `href`, as the title bars' glyphs are, so they are no interactive content inside the `<button>`; a press or a click on one is kept off the tab's own drag, resize and open (`.ms-tab-btn`, the guard the dialog's head uses for the links on it). The cluster is the board's alone, `.ms-tab-cluster` being shown under `body.dashboard` and nowhere else: `[G]` and `[S]` are its grid switches and mean nothing off it, and `[R]` is on every widget's own title bar and on its key. Behind the columns the tab is its name and no more. `[G]` and `[S]` are lit or dimmed by `syncMsTab()`, which `setGridPrefs()` calls wherever the switch was flipped — the dialog's tick, a key, or the glyph. The cluster is built before the tab is first measured, so it — with the `|` a `::before` on it sets between the name and the glyphs, inside the cluster so that it goes off the board with them — is part of the width `msTabMinWidth()` gives as the floor, and that floor follows the cluster off the board and back. Pulled narrower than the two together, it is the name that gives way — an ellipsis by `flex` and `min-width: 0`, the widget title's trick by another route. The tab can be dragged along the top edge and pulled wider or narrower by either side (`initMsTab()`: a press within `MS_TAB_EDGE` of a side resizes, elsewhere drags, through `trackPopoutPointer()`; no narrower than what its name and its cluster take together, which is also the width it hangs there at until it is pulled, `msTabMinWidth()` measuring it with the width unset so the floor and the starting width are one — no wider than `msTabMaxWidth()`, half the viewport — a share of the top edge rather than a fixed 300px, which was a stamp in the middle of a wide screen; read on every place instead of stored, so a window resized under the tab holds it to the half it has now, and a width stored on a larger screen comes back clamped. The floor beats the ceiling (`msTabWidth()`): on a narrow window the name and the cluster can take more than half of it, and a tab cut below what they need would ellipsise its own name for nothing. It is held inside the viewport, and a release that moved is no click), and where it was put is remembered in this browser only — `msTab` in localStorage, the left as a fraction of the viewport and the width in px — not in the arrangement, since it is about this screen and not the view; applied on load and on window resize. On desktop the dialog itself is a window on the same footing: dragged by its `.ms-head` (a link or a button on it is itself) and resized from any side or corner through the widgets' own `.po-h` handles, which `buildMapSettings()` appends to the panel — inside it, so the press that grabs one is a press inside the dialog and does not trip the outside-press-shuts rule — and `initMsPanel()` drives through `trackPopoutPointer()` with one listener on the panel, which outlives the rebuild its children do not. Nothing else about it changes: the page still holds still behind it and every way of shutting it stands. Until it is resized the height stays the content's, as the CSS had it, `placeMsPanel()` recomputing the `max-height` from wherever the top now is (the CSS's assumes the top the CSS set); a resize pins an explicit height, and only then is one stored. Where and how big is `msPanel` in localStorage — the left and top as fractions of the viewport, the width in px, the height in px once pinned — applied on open (measurable only once shown) and on window resize, so it cannot be stranded off screen; a press that never moved stores nothing, and a double-click on the head drops the lot and gives the CSS its dialog back. A phone gets the CSS's dialog: `POPOUT_MQ` gates the gestures and the apply, and the same media query gates the handles' `position: absolute`, so the ones in the markup lie flat. There the dialog fills the screen, so it drops its border — there is nothing left for an edge to divide it from — and its height is `100dvh` (with `100vh` before it for anything that does not know the unit), not `100vh`: `vh` is the taller viewport a collapsible URL bar is measured out of, which hangs the dialog's foot below the screen and the end of the body's scroll with it, putting the last of the preset management out of reach for good. The head gives its padding to its children rather than carrying it itself, so *Zatvori* is tapped anywhere in the right end of the bar and the title anywhere in the left — a word is a target for a cursor, not for a finger; both children keep the same top padding, so the baseline they are aligned on does not move and the bar reads as it did. The panel has two sections: the selected maps on top (this *is* the render order — drag the `≡` handle to reorder) and the available maps below (a finding surface only, sortable by name or category without affecting the render order; checking a map appends it to the selected block). Changing the selection or order auto-selects *Prilagođeno*, and dots the chip the list came from (`.ms-chip.ms-origin`, a `::before` at the left edge, clear of the corner triangle a saved preset carries at the same time) so the bar still names the view the edits are a copy of. Clicking the dotted chip reloads that preset and drops the edits — no extra handler: *Prilagođeno* holds the selection, so the origin chip is the unchecked one and its `change` fires normally. The selection deliberately does **not** stay on the origin chip: what a share link can carry for an edited preset is a bare list, not a name (a modified *Osnovno* is not `zadano`, and shipping `name: "Osnovno"` would plant a preset of that name holding different maps), so the flip to *Prilagođeno* is what tells you before *Podijeli* that a list travels. *Primijeni* saves to localStorage as `mapPrefs` (`{"preset":"radari"}` or `{"preset":"custom","maps":[…]}`), re-renders, and calls `initDynamicContent()` in `main.js` to wire the fresh DOM (lazy images, swipe, iframe src, overlays, link shadows, progress bar). `renderMaps()` takes any fullscreen map down first (`exitFullscreen()`, with layout persistence paused): the map goes with the tbody, and the page's scroll lock would otherwise stay behind it — now that the dialog is reachable from a fullscreen, this happens.

#### Saved presets

Below the picker sits the management list — *Zadani predlošci* first, then *Moji predlošci*, the order the preset bar puts them in — where the current selection can be saved under a name (`mapUserPresets`), then renamed, shared or deleted. Saved presets take the same `{ id, name, maps }` shape as the built-ins and are appended to them by `allPresets()`, so the preset bar, `presetMapIds()` and the stored preferences treat both alike. Their ids are prefixed `u:` to keep them out of the built-in namespace, which leaves the name free to change — renaming never breaks a saved preference. Saving under an existing name overwrites that preset, so the name is the handle: it is trimmed, collapsed and capped at `PRESET_NAME_MAX`. In the preset bar, saved presets carry a corner triangle (`.ms-chip.ms-user`, a `::after` so it costs no layout in chips that stretch and centre their names) — the same split the two management headings draw.

Amending a saved view has a direct path too: pick its chip, edit the list, and its row's *Podijeli* becomes an *Ažuriraj* link writing what is on screen over it. Both paths end in `storeUserPreset()` keyed by name, so preset contents have one write path, and the id survives — preferences and links naming that preset follow the change. The link hangs off `editingPresetId`, the preset the list was *loaded from*, not the bar selection, which editing flips to *Prilagođeno* (`markCustom()` re-renders the management list and re-marks the bar, so both marks track the edits). It shows only while the on-screen list differs from what is stored, and only on that row: an unrelated list must never overwrite a preset. `editingPresetId` holds built-in ids too, since they carry the origin dot — so the `isUserPresetId()` guard in `hasPendingEdits()` is load-bearing, not decorative: a built-in reaching `storeUserPreset()` would fork a saved copy of itself under its own name instead of updating anything. Note the build order it imposes — `fillList()` runs before `renderPresets()`, which reads the picker back to place the dot and would read an empty one as edited away from every preset. It replaces *Podijeli* rather than taking a fourth slot: three action columns are what fits a phone row beside the name, and a fourth drops every row's actions — built-ins included, since the slots only read as columns if all rows carry the same ones — onto a second line. Sharing is the one to give up while a row holds unsaved edits, since the row's link shares the preset *as saved* and the panel's own *Podijeli* covers the list on screen; it returns as soon as the edits are saved or dropped. Anything added here later has to replace a slot too, not join them. Like the rest of the panel it saves the preset only — the page still needs *Primijeni*.

Built-ins cannot be deleted (they are code) but can be hidden from the preset bar (`mapHiddenPresets`). Hiding is a **display choice only** — `allPresets()` keeps returning them, so a saved preference, the `zadano` fallback and a shared link naming a preset the recipient hides all still resolve; only `visiblePresets()` filters. `zadano` is exempt (`PERMANENT_PRESET_ID`) so the bar can never come down to *Prilagođeno* alone.

Deleting is the one panel action that writes to storage without *Primijeni*, so `deleteUserPreset()` also rewrites a `mapPrefs` naming the deleted preset into a `custom` snapshot of its maps — otherwise it would fail `isValidPrefs()` on the next load and silently fall back to *Osnovno*.

#### Share links

*Podijeli* copies a link with the current panel state URL-safe-base64 encoded in `?v=`. On load the parameter overrides saved preferences **for the session only** — it never writes to the recipient's localStorage. The parameter stays in the address bar (refresh-safe, re-copyable) and is removed via `history.replaceState` when the user applies their own settings. Clipboard API needs a secure context (https/localhost); elsewhere a prompt with the link is shown.

A built-in preset travels as its id, which every visitor resolves. A saved preset's id means nothing to a recipient, so it travels as its contents plus its name (`preset: 'custom'` + `maps` + `name`); the panel then offers to save it under that name, de-duplicated against the recipient's own presets so nothing of theirs is overwritten.

Arriving without an id, such a link would always open on *Prilagođeno* — including your own, where the list is a preset you already have. `activePresetId()` matches it back with `presetIdForMapIds()`: contents and order only (the name is a label the recipient may have used for something else, and a renamed preset is still the same view), saved presets searched before built-ins so a saved copy of a built-in list selects the copy. Matching also drops the offer to save it, which would only add a suffixed duplicate. Only the session-only shared view is matched this way — a `custom` in stored `mapPrefs` is a list the user chose not to save, and binding it to a preset id would hand later edits of that preset to a view that merely matches today.

Note when extending the payload: `btoa()` rejects code points above U+00FF, and the name is user-typed — every Croatian diacritic (č ć š ž đ) is above it. `encodeMapView()` escapes non-ASCII to `\uXXXX` before encoding, which keeps the input ASCII and needs no counterpart in `decodeMapView()`, since `JSON.parse` reads those escapes back on its own.

#### Pop-out widgets

On desktop every title bar carries a `[^]` button that lifts the map out of the table into a fixed, draggable, resizable widget, so one or more maps stay visible while the rest of the page scrolls. `renderMaps()` wraps each map's nodes (title bar, map, indicators) in one `.map-block` so there is a single element to lift; the links row below stays in the table. The button sits in the map-level title bar, or on each slide's title bar for titled slideshows without one (`buildTitleBar()`'s third argument). First in the cluster, shown only while the widget is popped out, an `[R]` (`.rl-btn`, `reloadMap()`) fetches the map afresh without reloading the page — the page may have been open long enough for new images to be out: images and video sources get a `_r=` timestamp parameter (`freshUrl()`, replaced on the next press) so the browser fetches past its cache, and a plain iframe is navigated to its `src` again. An interactive map's bar does not carry it: its own `[X]`/`[R]` gate button and behaviour (`main.js`) stay as they are. The clusters sit on the bar out of flow, so on a narrow widget the title would run under them: `fitTitles()` centres it in the gap between the clusters instead — from the pop-out on, so it never jumps between two centrings as the widget is resized — through a `--title-shift` the CSS folds into the title's transform, and gives it the gap's width as `max-width` (an ellipsis by CSS, scoped to popped-out bars) for when it is too long. It runs at the end of every gesture (`updateGroups()`, since a button coming or going changes a cluster's width), live during a resize and a column layout, and after a click or pointerup in the widget, which is what brings a slide's title bar on screen — a bar not on screen measures nothing and is left for then. `dockMap()` clears it (`unfitTitles()`).

`fitLetterbox()` is measured at the same moments and for the same reason, and the two go out together as `fitWidget()`, which is what those call sites call: both are the widget's chrome fitted to the box it has now. A letterboxed image is painted smaller than the element it sits in — `object-fit: contain` does that inside the box and lays nothing out, and CSS cannot see the result — so the arrows, absolute in the `.slideshow`, and the indicators, as wide as it, went on spanning the whole widget: the arrows hung over the bars beside the image and the indicators measured something wider than what they index. The painted rect is worked out here instead, from the natural ratio against the element's box, and published on the block as the four insets from the `.slideshow` the arrows are positioned in — which takes a slide's own title bar off the top for free, where `.shorter` used to — plus `--lb-w`, the painted width, for the indicators to take and centre themselves in and for the arrows to keep their 15% share of. The properties are scoped to `.letterbox` in the CSS, so a locked widget and a docked map are as they were, and `dockMap()` removes them with the rest of the inline state. One thing this needed: `.prev`/`.next` carried `transition: 0.6s ease` — *every* property — which was nothing while the arrows were fixed to their container and is a lag the moment they follow an image, sliding to the new place half a second behind a resize that had already finished. It names the two properties of the hover fade now.

Like the iframe fullscreen it is class-and-inline-style only — nothing moves in the DOM, which would reload an iframe. `popoutMap()` adds `.popout` (`position: fixed`), sets an inline `width` (`POPOUT_WIDTH`, or narrower if the block already was) and `left`/`top` at the block's on-screen position, so it reads as lifted rather than teleported, and drops a `.map-gap` spacer of the block's height after it, so the table does not jump; the spacer's *Vrati* and the button (now `[=]`) both call `dockMap()`, which removes the classes, the handles, the spacer and every inline property.

Resizing works from any side or corner through eight `.po-h` handles appended on pop-out, thin strips and corner squares straddling the edge. Two kinds of widget: images, slideshows and videos are *locked* — their height follows the width (`aspect-ratio`, `.vid1` padding), so `resizePopout()` only ever writes `width`, turns a pull on the top or bottom edge into the width that gives that height, and lets a corner follow whichever axis asks for more. That conversion is `lockedWidthFor()`, and it is read off the widget rather than taken from the start ratio: a locked widget's height is its title bar and indicators, which keep their height whatever the width, plus the map, which scales with it, so height is not proportional to width and the ratio is only an approximation — out by about the bar's share of the height, a dozen pixels, which is the whole of `MAGNET`, so a pull on the top or bottom edge used to land beside its magnet rather than on it. Setting the width and reading back the height it gave closes that, the error left being the bar's share of the error, so the second pass lands on the pixel; the height is read off the rect rather than `offsetHeight`, like `start`, so the two can be subtracted without a rounding costing the north edge a pixel. Iframes have no aspect of their own, so their widgets are *free* (`isFreePopout()`, `.free`): the block carries an inline `height` too, starting from what the `.if1`/`.if2` padding gave it at pop-out width, and lays out as a column in which the map takes what the title bar leaves. A locked widget is no wider than its content spans (`lockedMaxWidth()`, the ceiling `resizePopout()` clamps against and the one `resizeGroup()` holds each member to), for the same reason a locked pane in a column is (`fitSnapPane()`, `snapContentWidth()`): its height is its content's, so the aspect is locked to something only for as long as the content is still growing with it. The content stops at the map's `maxWidth`, which `maxWidthStyle()` writes inline — meteociel's 768, past which the whole widget froze at that height and went on widening under a lock on nothing — or, where the map sets none, at the image's natural width, which an `img` with no width of its own will not pass — neverin's 800, where the height did keep following but the image sat in the middle of a widget it no longer filled. What grows past that point is the frame's own ground beside the map, which is not a letterbox: that is the freed widget's answer and has the backdrop to show for it. The ceiling is measured by asking for it and seeing what the content took, since that is where both limits are written, and the widget is put back as it was so a rect taken before still holds. A free widget has none — an iframe fills whatever it is given. It cannot be measured before the images are there (an unloaded image gives its title bar the shrink-to-fit width of the words in it), so `applySnapLayout()` restores a stored width held only to the widget limits and `holdLockedWidth()` takes it in from the `load`/`click`/`pointerup` listener, which is also what follows a slide change to a narrower image; it only ever narrows, and stands down until the active image is `complete` with a natural width.

A locked widget can be freed too: a Shift-drag on any of its handles, while it floats, makes it a free widget for good (`unlockAspect()`: the inline height it has, `.free` — so every free-widget path applies, the height stored in the layout included — and `.letterbox`, under which the CSS undoes the inline aspect and `max-width` `maxWidthStyle()` writes — on the placeholder, and on the three other elements that carry the same cap: the widget's own title bar, the `.slideshow` container and the `.indicators-container`; an untitled slideshow's container is a `.placeholder` itself and was freed with them, a titled one's is not and kept the cap, so past the map's `maxWidth` it stopped growing, and a capped stretch in this flex column falls back to the start edge: the widget stretched on and the slideshow stayed at the left of it, taking the slide's own title bar and the image with it. The widget's own title bar was capped the same way and outlived that fix, being the one element a map with per-slide bars has not got: `buildMapTitleBar()` passes the map to `buildTitleBar()` and the per-slide bars do not, so the cap reached `.radartitle` on every map with a `titleHref` and a `maxWidth` — dhmz-radar, essl, estofex, meteo-si, dwd-sinopticka, idokep-radar-eu, istramet-munje, dhmz-sinopticka — and on no other. The four that looked right (neverin, astorp, meteociel, idokep's videos) have one or the other and not both, meteociel's per-slide bars being exactly the shape that was never in it. On the page the bar stands above a map held to that width and is held to it too; in a widget the map's width is the widget's, and the bar spans it. A double-click locked it again and centred it in the cap, which is why that read as a fix, and the next move with the board's grid snap on freed it straight back (`snapBlockToGrid()` unlocks the aspect: a locked widget's height can never reach a line of its own) and put it back at the left — and letterboxes the image, the active slide or the video in what the title bar leaves, over a blurred and darkened copy of the image on screen, a `.po-backdrop` painting `--po-img`, which `syncBackdrop()` follows on every load, click and pointerup in the widget, so a slide change or a reload's fresh address shows; a video has no image to take, and none can be read off it either — `drawImage()` from a `<video>` taints the canvas, `toDataURL()` then throws, and `crossorigin="anonymous"` would stop the video loading at all, idokep sending `Access-Control-Allow-Origin` for its own site alone — so where the map carries a `backdrop` that still frame stands in, which also covers a lazy slide whose `src` is not swapped in yet), and a plain drag on a freed widget's handle locks it again (`lockAspect()`: the height its aspect gives at the width it has, from the start of the gesture), as does a double-click on its title bar (the `dblclick` listener shared with the column edges; a link or button on the bar excepted), which works on a pane too — its stored height goes with the lock. The key decides per gesture, so nothing beyond the height a free widget already carries is stored; a stored entry with a height on a locked map is one that was freed, and `applySnapLayout()` frees it before placing it. In a column the width is the column's, so a freed pane stays free and resizes by its top and bottom edge like an iframe pane. Pulling the left or top edge keeps the opposite edge in place by moving the widget along; the new top is computed from the laid-out `offsetHeight`, so it is exact for locked widgets as well. Dragging is a `pointerdown` on a non-fullscreen `.radartitle` inside a `.popout` (links and buttons excluded); both gestures share `trackPopoutPointer()`, move/up listeners on `document`. `preventDefault()` on the `pointerdown` also suppresses the compatibility `mousedown`, so a drag by a slide title bar cannot register as a swipe on the slideshow around it, and `body.po-dragging` turns iframe pointer events off so the pointer is not swallowed mid-gesture. Any `pointerdown` on a widget raises it (`popoutZ`) — except one hosting a fullscreen map, which is kept under the others (see below). No widget draws its own shadow: drawn by the widget it was painted in the widget's own place in the order, so of two widgets side by side the raised one laid its shadow across its neighbour, and the only way to be rid of it was to raise the neighbour in turn. Instead every floating widget has a box of its own rect in one fixed layer (`.po-shadows`, `z-index: 4900`) which carries the shadow — over everything that is not a widget (the page and the docked maps on it, the columns' ground, the board's graph paper, a fullscreen map at 4500/4501) and under the whole widget range, which starts at 5000 — so every widget is over every shadow whatever the order among themselves. An outer `box-shadow` is clipped out of its own border box, so a box paints the halo alone and the widget stands on it exactly; the rect is taken as it is, thousandths of a pixel included (`subpixel()`). `syncShadows()` places the boxes and sweeps out any left without a widget — one docked, or gone with the tbody — and runs off the end of `updateCovered()` (the same call sites: wherever a rect or the order can have changed), off `trackPopoutPointer()`'s move, so the shadows follow every gesture live, off the `load`/`click`/`pointerup` handler, where a floating locked widget's height changes with its slide, and off `dockAllPopouts()`, which the breakpoint reaches with persistence paused. And off the guard in `applySnapLayout()` for an arrangement with nothing in it, which returns above that `updateCovered()`: what the arrangement replaces went with the tbody rather than being docked, so leaving the board with nothing placed left every widget's shadow behind on the page it came back to. A pane in a column has no box (docked into the column's ground rather than floating over it), nor has a widget hosting a fullscreen map, whose box is not to be seen. An iframe takes the pointer itself, though, and a press inside it belongs to the frame's document: the page never sees it, so a widget whose map is an interactive frame could not be clicked to the front. Most maps are spared by their gate, the `.overlay` over the frame that takes the press, but a basic iframe (`.if2`) has none and an interactive one loses its own once the gate is let through. Nor can the page be told after the fact: the focus moving from one frame straight to another raises no event it can hear, the window having none left to lose. So a widget with another lying over it hands the pointer back — `updateCovered()` marks it `covered` (any widget of a higher `z-index` whose rect meets its own; a fullscreen host excepted, its map being the one thing meant to be used) and the CSS takes `pointer-events` off its frame. The press then lands on the widget and raises it, the mark goes with the raise, and the frame is live for the next press: click it to the front, then work the map, as a window does. A widget nothing overlaps is never marked, so a map standing on its own is untouched — and for that one a `blur` on the window, with an iframe left as `document.activeElement`, still raises its widget, which keeps the order honest for when something is dragged over it later. `updateCovered()` runs with `updateGroups()`: off `raisePopout()`, off every gesture through `persistSnapLayout()`, off the window-resize clamp, and at the end of `applySnapLayout()`, where persistence is paused. `placePopout()` clamps into the viewport, on drag and on window resize alike. Positions are written to the thousandth of a pixel rather than the whole one (`subpixel()`, used by `placePopout()` and `moveGroup()`, the drag's own placer): a locked widget's height is its title bar plus the width over its aspect, so its bottom edge lands on a fraction, and a widget magneted under it used to be put half a pixel into it — both borders drawn, a seam about one and a half wide, which is what a whole-pixel landing costs. Only a landing on such an edge carries a fraction; a width is whole, so the sides are, and an ordinary drag stays on the grid. What is left is the layout unit (1/64px) on a fresh drag and about a thirtieth of a pixel through a store and restore, where the stored fractions are rounded to four places. Away from the viewport edges the other floating widgets are magnets (`magnetPosition()`, within `MAGNET`): an edge brought close to another widget's opposite edge is pulled onto it — beside it when the two overlap in height, above or below it when they overlap in width — and once they meet on one axis the nearer of the like edges lines up on the other, so a widget dropped below another sits flush with its side. The closest edge wins per axis; the others' rects are read once at the start of the drag (`magnetRects()`, panes and fullscreen hosts left out), and the pull only starts past `SNAP_ARM`, like the column snap, so a click does not move a parked widget. A drag never changes a size — the widget is moved onto an edge, not fitted to it — but a resize has the same magnets on the edge being pulled (`magnetEdge()`): it lands on the facing edge of a widget beside it (above or below it, for a top or bottom edge) or in line with the like edge of a widget above or below it, exact for a width, and for a locked widget's height too through `lockedWidthFor()` above — whose width, once the height has asked for it, has a moving edge of its own (the right one, or the left pulled from the west) that is pulled again, so a locked widget under a wider one lines up with it by that edge from its bottom handle too. It holds the other way about as well, since a locked widget's two axes move together whichever one is held: a width pulled by a side handle carries the bottom edge down with it (the top edge up, from a northern corner), so that edge is offered the same magnets and the width is taken back from the height that lands on one (`lockedWidthFor()` again) — which is how a widget widened beside a taller one stops level with its bottom rather than sliding past it. Either way the *derived* edge's pull is the last word, and a pull that reaches no magnet leaves the gesture as it was. `pullResizeEdges()` is the shared pull throughout; only a pure `n`/`s` drag skips the second, vertical one, its height being the edge already pulled.

Widgets that touch — an edge of one on an edge of the other, overlapping along it (`rectsTouch()`, within `GROUP_TOUCH`), which is what the magnets leave — can be *grouped*, explicitly only: the title bar's `[+]` (`.grp-btn`, first in the cluster, shown by `updateGroups()` only on a widget touching another or in a group; `[-]` on a member) joins the widget with what it touches, and with their groups, into one (`joinGroup()`), and `[-]` takes it out (`leaveGroup()`; a group left with one member is dissolved, and a group whose middle leaves stays a group though its ends no longer touch). Widgets touch only in one place — floating over the page, or panes of the same column (`touchingBlocks()` looks no further) — so a group is always in one place. A group lives in `block._group`, an id shared by its members, and shows as `.grouped` (the frame in the snap blue; it keeps its shadow, which since the shadow layer falls under the member beside it rather than across it). It drags as one: `dragPopout()` moves the members by one offset (`groupStarts()`/`moveGroup()`, or `movePanes()` in a column), with the magnets, the viewport clamp and the column snap seeing the group's bounding box (`groupBox()`) rather than the widget held; dropped at a viewport edge it goes into the column as a stack and stays a group, and pulled out of a column it floats as one. It raises as one too (`raisePopout()` brings the members up in their order), and the window-resize clamp moves a floating group by its box. It resizes as one too (`resizeGroup()`, off any member's handle while the group floats): the box is pulled as a locked widget's is — one scale for the whole, from the pulled axis, a corner following whichever asks for more, from the edge or corner opposite the one pulled, the other widgets its magnets, and the scale held so no member goes under its minimum width or height, none over `POPOUT_MAX_WIDTH`, and the box stays in the viewport — and every member is scaled by it (a free one in height too). A locked member's height follows its width with the title bar not scaling along, so the scaled offsets alone would open hairline gaps in a stack: each member is placed at its scaled offset and then settled onto the members it touched or lined up with before (`groupRelations()`, read at the start of the drag: below/above/right/left by the touching edges, the alignments along them first, the touch last so it wins an axis), in top-then-left order, so a stack stays a stack. In a column a group is a *stack*: every layout of the column (`settleSnapStacks()`, from `layoutSnapColumn()`) sits the members one under another in the order of their tops, from where the first stands, and holds the stack inside the viewport by its bottom (by its top when it does not fit), the tops the members carry following — so the column's width or the window changing under a stack changes its members' heights and not their touch, and a stored stack comes back as one whatever the viewport. A free pane in a stack still resizes on its own, the stack keeping together: the members above it move up with its top edge, the ones below down with its bottom edge (the settle), and the stack's ends stop at the column's; the members are no magnets for it, since they move along. Since a stack is contiguous, a middle member leaving splits it (`leaveGroup()`): the members above it and the ones below are each a group of their own, when two or more. Docking a member takes it out of its group. In the stored layout a group is a number shared by its members' entries (`group`, counted in order of appearance over the columns and the floating widgets; `sanitizeSnapLayout()` drops one left with a single member or spread over two places), mapped back to fresh ids on restore.

Desktop only: `POPOUT_MQ` (`min-width: 801px` plus `hover: hover` / `pointer: fine`) gates `popoutMap()` and, as the same media query in CSS, the button's visibility; shrinking below it docks every widget. Widgets are session state — *Primijeni* re-renders the tbody and they go with it.

#### Snap columns

A widget dragged until its own edge reaches the left or right edge of the viewport (`SNAP_EDGE`, 5px, wherever the bar is held — the position the pointer asks for is checked, not the clamped one, so pushing on past the edge still counts; and only after `SNAP_ARM` of movement, so a click on a widget parked at the edge is a click) snaps into a column there — on the page only, the board having no columns (see below): a strip of the viewport's height in which panes sit freely one above another, the page laid out in what is left between the columns (`body` padding through the `--snap-l`/`--snap-r` custom properties, so the table centres in the remaining width). Sizes come from `viewportWidth()`/`viewportHeight()`, the document's `clientWidth`/`clientHeight`: `innerWidth` counts the vertical scrollbar, under which a right column (and a floating widget clamped by `placePopout()`) would otherwise land. A pane is still a pop-out widget — same block, same classes, same fixed positioning, nothing moves in the DOM — only its width is the column's and its place comes from `layoutSnapColumns()` instead of a gesture. `snapColumns` holds per side a `width` and a list of `{ block, top, height? }` panes, every number a fraction of the viewport so a window resize keeps the proportions; a free pane carries its height, a locked one's follows the width. A pane's top is its own: up and down the column it is dragged as a widget is over the page, with the column's ends and the other panes' tops and bottoms as magnets (`paneMagnetEdges()`, `paneTop()`, which `movePanes()` applies to the dragged panes' box), and a free pane's top and bottom handles resize it against the same edges (the side and corner handles are hidden in a column by CSS, all of them on a locked pane). The drop is previewed by `.snap-preview` at the slot `snapSlot()` gives — the column's width (a new column takes the widget's own, clamped to what the other column leaves), the top the widget's box asks for pulled to the column's magnets, and the height the dropped widgets stack to at that width — and `snapPanes()` stacks them there in top-then-left order, each under the one before, so a group drops into a column as one and stays a group.

Two fixed elements per column: `.snap-col` paints the column's ground below the panes, `.snap-ui` above them holds the handle (`pointer-events: none` on the wrapper, `auto` on the strip) — the inner edge (`resizeSnapColumn()`, up to everything the other column leaves). A fullscreen map fills its container rather than the viewport: the CSS puts `.radartitle.fullscreen` and `.if1.fullscreen` between `--snap-l` and `--snap-r` (zero elsewhere, so the landing page and a page without columns are as before; `.if1`'s `width: 100%` has to be undone there or it beats `right`), and a pane's `.snapped-left`/`.snapped-right` class moves them over its column, which follows a column edge drag live — over what the column leaves free around the pane, not the whole column: `fitSnapFullscreen()` (from `layoutSnapColumn()`, so a pane moved or a column resized meanwhile is followed) sets `--fs-top`/`--fs-bottom` on the host to the bottom of the panes above it (their top over the host's, one lying over it included, since it stays on top) and the top of the panes below it, the column's ends where there are none, and never less than a map's minimum height, and the CSS puts the bar and the map between them; under `body.snap-full` a floating widget's fullscreen takes the whole viewport, since the page it would fill has none. On the board it does not: `fitBoardFullscreen()` sets all four of `--fs-left`/`--fs-right`/`--fs-top`/`--fs-bottom`. The map takes the whole viewport there, and a side comes in only where another widget *walls it off* — where the widgets on that side, together, cover the rectangle from end to end of its other axis (`freeRectAround()`). A wall is what makes a region a region: a widget down the left of the screen leaves the right half a place of its own, and a map filling it is filling what it is in. A widget that does not reach across walls nothing off and is floated over — one in a corner leaves no region behind it, and taking a whole screen's map down to the space beside it would be giving up the screen to a tile; nothing is lost by covering it, since the widgets keep their `z-index` range above the fullscreen and it stays where it is, over the corner of what is now a map of the whole board. A widget lying over the host is on no side of it and so is never a wall, which is the same answer for the same reason. The walls are looked for again once the sides have come in, since narrowing the rectangle is what lets a widget reach across it — one over the right half alone walls off nothing of the viewport and walls off the top of a rectangle that is already the right half — and it settles in a pass or two, every pass only narrowing. Coverage allows a gap of `POPOUT_MARGIN`: that is the margin the sizing clamp keeps off the viewport edge, so a widget stored at the full height comes back exactly that much short of it and would otherwise stop walling the moment the page was reloaded, and it is the grid's cell besides, so widgets stacked on the grid wall as the eye reads them. There is one wall search and not four — the other three sides are the left one under a mirror, a transpose, or both. The host's own box is still there to read under its fullscreen, its bar and its map having gone `position: fixed`, because every map with a `[ ]` is an interactive one and an interactive map's widget is always free (`isFreePopout()`) and carries an inline height; a locked widget given a fullscreen would collapse to its content and need its rect kept from before. It is fitted again on the `map-fullscreen` event and from `updateCovered()`, so a widget moved or raised beside a fullscreen map changes the rectangle it fills, and the properties are cleared off every floating widget that is not hosting one — including a pane that has been floated since, which is where `fitSnapFullscreen()` left its two. `toggleFullscreen()` in `main.js` locks the page scroll only for a map not in a pane — beside a column-filling map the page stays in use — and both it and `exitFullscreen()` dispatch a `map-fullscreen` event, on which `popout.js` marks the widget hosting a fullscreen map `.fs-host` (only the bar and the map move to the fullscreen place; the widget's box — frame, shadow, handles — would stay behind, an empty frame over whatever it was floating on, so it goes `visibility: hidden` with the two fullscreen children visible again). The widgets floating over the page stay in view over a fullscreen map, whichever map it is: on desktop the CSS puts the fullscreen classes under the widgets' `z-index` range (`4500`, above the columns' ground), and since a widget's own fullscreen stacks inside the widget's context, the host is lowered to the same place (`POPOUT_FS_Z`, the `pointerdown` raise skipping it meanwhile) and raised again when the fullscreen ends — a fullscreen map never covers another widget, only the page or its column. The same handler has `layoutSnapColumns()` re-lay the columns out to a viewport the scroll lock's scrollbar toggle has just changed. The bar's `[=]` is hidden in fullscreen as before; the spacer's *Vrati* still docks such a pane, and `dockMap()` takes the fullscreen down first. A free (iframe) pane takes the column's width with the height it carries, through the inline height `.free` lays out; a locked one takes the column's width and the height its aspect gives at it, pulled in to what its content spans (`fitSnapPane()`, `snapContentWidth()`: the narrowest of the visible title bars, which carry the map's `maxWidth`, and images or videos, which stop at their natural width — otherwise the title bar and indicators would run on across a column wider than the image), and sits centred in the column; either is held inside the viewport by its top. A locked pane's height can change under the fit — a titled slideshow takes its width from the image and changes aspect with the slide — so a `load`, `click` or `pointerup` inside a locked pane lays the columns out again.

The columns can take the whole width — two meeting, or one at full width — which hides the page: `isSnapPageHidden()` reads it off the width fractions summing to one (so it does not depend on the pixel viewport, which changes at that very moment: `body.snap-full` drops the page's scrollbar, and `layoutSnapColumns()` toggles the class before measuring). An edge dragged within `SNAP_SHUT` of what the other column leaves snaps shut, and the width is then set to exactly `1 - other` so the state reads. Two columns that meet share one seam handle — the left column's edge with `.snap-seam`, the right one's hidden — that moves width between them (`resizeSnapSeam()`); a double-click on any edge hides the page (this column takes what the other leaves) or, when it is hidden, brings it back to the widths from before (`snapPageWidths`, kept by the drag or the click that hid it) — failing those, the columns are scaled down to leave the table's width. The browser's `dblclick` is used as is: the drag's `preventDefault()` on `pointerdown` leaves it alone, and the browser already tells a double-click from two drags apart.

Dragging a snapped pane's title bar moves it up and down its column until the drag goes `SNAP_DETACH` sideways, then `unsnapPane()` floats it again as it stood — size and place kept, the title bar under the pointer — and it can be dropped straight back into the column, or the other one. `dockMap()` unsnaps first, so the `[=]` button, the spacer's *Vrati* and the breakpoint work on panes as on widgets; `renderMaps()` calls `resetSnapColumns()` since the panes go with the tbody.

#### Remembered and shared layouts

The arrangement is part of the view, so it travels with the map list rather than as a thing of its own: `snapLayout()` serialises the columns (per side the width and the panes as map ids with their height shares) and the widgets floating over the page (`floating`, bottom to top so they stack the same way again: id, left, top, width, and a height for a free one — a locked widget's height follows its width), every number a fraction of the viewport rounded to four places, null when nothing is popped out. A pane or a floating widget hosting a fullscreen map (`.fs-host`) carries `fullscreen: true`, so a view saved or shared from that state comes back in it: `sanitizeSnapLayout()` keeps the flag only on an interactive map (`hasFullscreen()`, by catalog type), and `applySnapLayout()` puts the flagged maps fullscreen last, once everything stands where it belongs (`restoreFullscreen()` clicks the map's own `.fs-btn`, so `main.js` does all a click does — and reads off the attached pane whether to lock the page's scroll) — and it sits as `layout` next to the list in `mapPrefs`, in a saved preset (`{ id, name, maps, layout }`) and in the `?v=` payload. It is always a subset of the list it sits beside, and `sanitizeSnapLayout(layout, mapIds)` holds every copy read back to that — storage, links, saved entries: a pane or a floating widget must name a map in the list, once across all of them, panes up to the cap; shares are renormalised, the widths bounded to the viewport, a bad width drops its column, a floating entry with a number out of range is dropped, and a map dropped from the list leaves the layout. `applySnapLayout()` rebuilds it all from a clean layout after a render (each pane popped out and attached as it stands through `attachSnapPane()`, then widths and shares set as stored; each floating widget popped out, sized within the widget limits, placed and raised in order), with persistence paused, since what is being applied is what is stored; on load, `applyStoredSnapLayout()` does this on `DOMContentLoaded`, registered after the render so the maps are there — and after `main.js` has run in dev, since the snap code logs through `dlog()`. Desktop only, like the gestures: a phone carries the layout and does not show it.

The arrangement is written as it changes (`persistSnapLayout()` at the end of every pop-out and dock, drag and resize, snap, handle drag and page toggle, and on the `map-fullscreen` event on desktop — a phone has no arrangement on screen, and writing its empty one would drop the stored desktop layout — `unsnapPane()` itself leaves it to its callers, which end in a state of their own) — it is direct manipulation, not a form with an apply button — into `mapPrefs` next to whatever list is there. Under a shared view it goes into `sharedMapView` and back into the address bar instead, so the link stays re-copyable with the arrangement as it is now and a refresh keeps it, while the recipient's storage is still never written. The breakpoint docking everything runs with persistence paused (`snapPersistPaused`): that is the window changing, not the arrangement, and the stored layout is kept for a desktop window. Kept, and held: below the breakpoint `applySnapLayout()` places nothing, so the board stands empty while the preferences still describe a desktop arrangement, and `snapLayout()` — which reads the screen — would describe that emptiness and write it over what is stored. The arrangement it cannot show is parked in `unappliedSnapLayout` instead (by `applySnapLayout()` on a narrow load, and by the breakpoint handler on the way down, read before the dock empties the board), and everything that writes the arrangement or asks what the view holds goes through `currentSnapLayout()`, which answers with the parked one while there is one. Widening applies it and clears it, so the widgets and the board come back as they were, and the screen is the truth again.

*Primijeni* decides which arrangement the new list gets (`layoutForPrefs()`): a preset is a whole view, so a saved one brings its own — none, if it was saved with nothing popped out — and a built-in, which has none, docks everything; only the custom list keeps the one the view holds (`currentSnapLayout()`, so a *Primijeni* pressed on a narrow window keeps the parked arrangement rather than replacing it with the empty screen), as far as its maps allow, since that is an edit of the current view rather than a switch to another one; it goes into the preferences with the list and `applySnapLayout()` brings it back after the render drops the panes. The mode is the panel's rather than the arrangement's, and `withDashboard()` puts it on whichever layout is going out (see the board, below); the row starts from `isDashboardView()`, which below the breakpoint is the parked layout's mode rather than the screen's, so the dialog does not open with the board ticked off and apply that. Saving a preset (*Spremi*, *Ažuriraj*) stores the arrangement on screen held to the list in the picker and to that toggle (`selectedLayout()`), and `hasPendingEdits()` counts a changed arrangement as an edit, so a rearranged page offers *Ažuriraj* on the preset it was loaded from — only there, though: the origin dot on the chip marks a changed list, which is what the panel itself edits. Sharing carries it the same way: the panel's *Podijeli* with the list on screen, a saved preset's row with the preset's own (`presetSharePrefs()`), and a recipient who saves the shared view keeps it. The panel's one sign of all this is the `.ms-layout` line naming what is popped out (*Izdvojene karte: lijevo 2, desno 1, u prozoru 1*) with *Vrati sve* to dock it all — and, above it, the `.ms-mode` row for the board (below): another way of viewing altogether, so it is a button in a band with a blue edge rather than a link among the others — but a *toggle*, not a way onto it. It ticks `dashboardChecked`, a pending value of the panel like the ticks in the list beside it, and nothing on screen moves until *Primijeni*. The row never narrates, and carries no prose at all: the button's label stays *Nadzorna ploča*, and whether it is ticked is `aria-pressed` and the lit `.ms-on` band's to say, what is popped out the layout line's. Beside it sit the board's two grid switches, *Prikaži mrežu* and *Poravnaj uz mrežu* (`.ms-grid`), which mean nothing off the board and are `disabled` and dimmed (`.ms-off`, a class rather than `:has()`) while it is unticked — their own ticks kept all the same. Unlike the mode beside them they take effect on the tick rather than on *Primijeni* — they say how to work on the board, not what it shows, so there is nothing to hold back: tick the grid on, see it, shut the dialog. (`setGridPrefs()` writes and draws in one go; with the board not yet on there is simply nothing to draw, and `setDashboard()` draws it when it arrives.) That line still stays out on the board. Both rows are hidden by attribute on a phone (`POPOUT_MQ` not matching), which the CSS restates as `display: none` for `[hidden]`, since their `display: flex` would beat it.

#### Dashboard

The *dashboard* (*nadzorna ploča*) is the page out of sight and every map of the list a floating widget — a mode of the view, not a page of its own: `dashboard: true` on the layout, so it rides with the list in the preferences, a saved preset and a share link, `sanitizeSnapLayout()` keeps it (a board with nothing placed yet is still a board), and `applySnapLayout()` brings it back — the mode set first, since the page's scrollbar goes with it and changes the viewport everything after is measured in, then the stored entries placed, then every map of the list the layout does not place popped out onto the board (`popoutRest()`: one after another down a cascade of `CASCADE_STEP` from the top left of what the columns leave, back to the top once the widget in hand would run off the bottom, each round half a widget further right — the step is the cascade's own running count, since a number of steps worked out per widget is a different modulus for every height and lands several of them on one place), which is also how a map added to the list in the dialog arrives. `body.dashboard` (`setDashboard()`) hides the page and everything on it by `visibility` (not `display`: the widgets are inside the table and have to stay rendered — `.map-block.popout:not(.fs-host)` is made visible again), locks its scroll, shows the `.ms-tab`, and lets a floating widget's fullscreen take the whole viewport as under `body.snap-full`. None of that can run until the maps are rendered, which is `DOMContentLoaded`, and by then the browser has usually painted what it had — so a board opened over a slow connection showed the ordinary page for a tenth of a second before taking it away. `cloakBoard()` closes that: the list and its layout are in storage or in the `?v=`, so whether a board is coming is known while `<head>` is still being parsed, and `html.board-boot` hides the same `.container` and `footer` from then until the arrangement is applied. It comes off on `DOMContentLoaded` in a listener of its own, registered after the one that applies the layout, since listeners run independently and a throw in the apply must not leave the page hidden behind a board that never arrived. Measured on a throttled load of the built page: seven or eight painted frames of the page, a hundred milliseconds of it, against none. In dev the scripts are external and deferred, so the cloak is set after the body is parsed and the flash can still show; the build inlines them into `<head>`, which is where this works. A board has no snap columns: a column is a strip the page makes room for, and there is no page there to make it. `snapSideAt()` returns nothing while the mode is on, so no drag targets a column and a widget taken to the viewport edge simply stays a widget, and `sanitizeSnapLayout()` drops `left`/`right` from a board layout, so a page arrangement ticked onto the board — or a stored board from before this held, or a hand-edited one — comes back with its panes as ordinary widgets, placed by `popoutRest()` among the rest. The columns are the page's alone, and are there again the moment the mode goes off. Which is the only way onto it: the dialog's mode row ticks the mode and *Primijeni* applies it with the list, so nothing enters the board on its own. It is left the same way, or by docking everything (`dockAllPopouts()` drops the mode first, for the scrollbar, then docks — so *Vrati sve* and the breakpoint leave it, the latter with persistence paused so the stored view keeps the mode for a desktop window), The board can be worked on graph paper: `GRID_CELL` (16px) gives the lines, and they are a *size* rather than a count, so they fall on whole pixels by construction whatever the window, the cells stay square on every screen, and the paper is one `repeating-linear-gradient` however fine it gets (`.po-grid`, fixed, `z-index` under the widgets and over the columns' ground, hung off `body` rather than the `.container` the board hides). `Prikaži mrežu` draws it; `Poravnaj uz mrežu` settles a widget onto it — on release only, never while the gesture runs, off the end of `dragPopout()`, `resizePopout()` and `resizeGroup()` (`snapToGrid()`). Each of the four edges goes to its nearest line (`gridLines()` are the multiples of the cell *and* the far edge itself, which is the page's and rarely a multiple), so the widget grows or shrinks to fit rather than being moved as it stands, held to `POPOUT_MIN_WIDTH`/`POPOUT_MIN_HEIGHT` by taking the next line out. A locked widget is freed first (`unlockAspect()`): its height follows its width and could never reach a line of its own, and at this cell the letterbox that leaves is a few pixels. Two edges land on the same line whenever they lie within half a cell of each other, so the grid forgives 8px — many times the fraction of a pixel an aspect-derived height leaves between two widgets — which is what makes a snapped board exact where a placed one is only nearly so. `popoutMaxWidth()` also lifts `POPOUT_MAX_WIDTH` on the board: that cap is the table's width, and a board of half-width tiles on a wide screen needs more than 875. And `resetSnapColumns()` drops the board with the panes when the tbody goes, for `applySnapLayout()` to set again. On the board the widget's `[=]` is `[x]` (`setPopoutButton()` reads the mode) and takes the map off the list (`removeFromDashboard()`: the widget docked, its rows — block, links, one spacer — removed from the hidden table, then `removeMapFromList()` in `maps.js` stores the custom list without it, into the preferences or the shared view, and writes the arrangement after it), so the other maps are not re-rendered and their iframes not reloaded. *Primijeni* decides the mode along with the arrangement, but from the mode row's toggle rather than from the layout going out: `layoutForPrefs()` picks the arrangement as it always did — the custom list's is the one on screen, a saved preset's its own, a built-in's none — and `withDashboard()` then sets the mode on it, before `sanitizeSnapLayout()` rather than after, so what it marks a board is held to what a board can hold by the same guard every layout read back from storage or a link passes. Ticked, any layout becomes a board, a built-in's nothing included, which `applySnapLayout()` fills with every map of the list; unticked, a board loses its placements along with the flag (`null`, so everything docks), since a board holds the whole list as widgets and over the visible page that is a pile rather than an arrangement. A page layout is left alone either way, so a preset saved with two widgets keeps them where they were and the rest of its list cascades in around them. Picking a preset chip sets the toggle to that preset's own mode, the way it sets the list — a saved board ticks it, a saved page and every built-in untick it, *Prilagođeno* leaves both alone — so a built-in on a board is the chip first and the toggle after. A changed toggle is a pending edit like a changed list: it goes through `selectedLayout()` into what *Spremi* writes, what `hasPendingEdits()` counts (so *Ažuriraj* appears on flipping the mode of the preset the list came from), and what the panel's *Podijeli* carries — the per-preset rows' links still share the preset exactly as saved. A saved preset that is a board (`isBoardPreset()`, the flag on its stored layout) carries the board's mark — the mode row's blue left edge, `.ms-board` — on its chip in the bar and on its name in the management list, with *Nadzorna ploča* as the title. The panel is rebuilt on every open, but the arrangement changes behind it while it is open — a map popped out, a pane snapped — so `persistSnapLayout()` calls the open panel's `_onLayoutChange()`, which redraws the line and the management rows, and *Ažuriraj* appears or withdraws at once.

#### Keyboard and the title bar's gestures

Keys are for what the buttons cannot do in one gesture, and for backing out of what covers the screen. The letters name the thing and not the word for it, so they stand whatever language the page comes to speak: `R` is the `[R]` the bar already carries, `G` the grid and `S` its snap. (`K`, which opens the dialog, was there before this and is the Croatian *Karte*.) The three are also the tab's glyph cluster — `[R] [G] [S]`, each titled with its key — which is where they can be read off. The dialog keeps `K` and its own Escape in `maps.js`; the rest live in `popout.js` behind the same two guards — never from a text field, whose own Escape is a way out of the field, and never under a modifier, which belongs to the browser — and everything but Escape behind `POPOUT_MQ` besides, the widgets being a desktop thing. None of it reaches the page while an iframe holds the focus: a press inside a frame belongs to the frame's document and these maps are another origin, so a click on the page or on a title bar comes first, as it does for the pointer (see `updateCovered()`).

`Escape` ends a fullscreen map (`escapeFullscreen()`). It is a class here and not the browser's own fullscreen, so nothing else would; the dialog is over everything and keeps Escape while it is open, and under a fullscreen Escape does nothing at all — backing out is not a reason to take an arrangement apart. `R` reloads every widget whose bar offers `[R]`, once each (`reloadAllMaps()`; a titled slideshow carries one on every slide). An interactive map carries none, and `reloadMap()` reaches only a basic iframe (`.if2`) among the frames, so this is the images, the slideshows, the videos and the basic frames — what has to be fetched again to be new. An interactive map's own feed is live, and navigating its frame again would cost it its pan and its zoom for nothing. `G` and `S` toggle the grid and its snap (`toggleGridShown()`, `toggleGridSnapped()`), and only on the board: off it the dialog's switches are greyed and unclickable, the tab's are not shown at all, and the keys are as quiet — a switch flipped where nothing shows it being a switch lost. The two switches stand in three places now, so `setGridPrefs()` tells the two that were not used: `syncMsTab()` lights or dims the tab's glyphs, and an open dialog, which holds its own copy of them, is re-read through the panel's `_onGridChange()` — beside `_onLayoutChange()`, and for the same reason: without it the next tick would write the stale copy back and undo what the key or the glyph did.

The arrow keys nudge the widget on top (`topPopout()`, `nudgePopout()`) — except while the dialog is open, when they are its own: its body is the only thing that scrolls there, and an arrow pressed on the map list is not aimed at a widget behind it, so the handler stands down (`mapSettingsOpen()`, which `escapeFullscreen()` asks the same question of) rather than moving a widget out of sight and taking the key from the scroller. `G` and `S` above it are the other way about, the dialog carrying those two switches itself and being re-read when they change. `popoutZ` already names the widget on top and the shadow layer leaves it unmistakable, so it carries no mark of its own: the press shows which it was, and a click on another picks another. A pane is out of it, living in its column where a top is not a place, and so is a widget hosting a fullscreen map. The step is one `GRID_CELL`, so a board snapped to the grid stays snapped, and one pixel with Shift for the placement the lines have none for; a group moves whole, as it does under the pointer, and the viewport holds it the same way. `updateCovered()` runs at once so the shadows and the order follow, while the arrangement is written on a 300ms timer (`nudgePersist()`) — a held arrow repeats, and each repeat would otherwise be a write.

A widget is a window, and its title bar carries two gestures beside the drag. A double-click on it puts the map in fullscreen and takes it out again, through the bar's own `[ ]` button, which keeps its label and the snapshot of the overlay gate; `toggleFullscreen()` reads the class, so one press does both ways, and the bar is still on screen in fullscreen to leave by. A middle click is the bar's `[=]`/`[x]` without having to aim at two characters — `togglePopout()`, so it docks on the page and takes the map off the board, which is what that button means in each place. Both are on the bar alone and never on the map: over a frame the page would never see them, and on an interactive map a double-click is already the site's own gesture for letting the overlay gate through (*Dvostruki klik za pristup interaktivnoj karti*) and then the map's own zoom. A link or a button on the bar is itself (`titleBarOf()`), as it is for the drag — the title is an `<a>` to the source, and a middle click on it belongs to the browser. The middle button raises the autoscroll cursor on press, so the `mousedown` is taken and the action left to `auxclick`. The fullscreen double-click shares its element with the aspect lock's (a freed widget's bar, locked again by a double-click) and can never be the same widget: only an interactive map has a `[ ]`, and an iframe is always free (`isFreePopout()`) and so is never letterboxed.

#### Touch notes

Hard-won details worth keeping in mind when touching the drag/scroll code:

- the drag handle must not be `display: inline` — `touch-action` is ignored on non-replaced inline elements, so touches would scroll the page instead of dragging
- pointer capture cannot be used for the drag: touch pointers implicitly capture the handle, and any capture breaks once the row is moved in the DOM (`insertBefore`). The implicit capture is released on `pointerdown` and move/up listeners live on `document` instead
- `scrollIntoView` scrolls *all* ancestors, so it cannot be used to reveal something inside the panel — it drags the page back up to the panel too. The preset bar used to scroll horizontally and needed a hand-rolled reveal for this reason; it now wraps its options as chips instead, growing in the axis the page already scrolls, and the reveal is gone

### The manual

[`MANUAL.md`](./MANUAL.md) is the user-facing document: what the site does and how to work it, in Croatian, which is what the site speaks. It sits at the root beside `README.md` and this file, and is named to match them — *what it is*, *how to use it*, *how it works*. It deliberately cannot live in `docs/`, the conventional place for it, because `docs/` is the built site and `build.ps1` deletes it on every run. The file name stays English for the same reason the rest of the repo is, and to leave room for a `MANUAL.en.md` beside it.

It shares no prose with this file on purpose: this one explains mechanism to someone reading the code, that one answers *how do I keep two radars side by side while I scroll?* Every UI label it quotes is the label the code renders, so a label that changes is one grep from the line that quotes it.

#### The manual on the site (not built yet)

The plan is that the Markdown stays the only source and the build makes a page of it — one new step, since the component machinery already does this job. What is prepared for it: the document uses `##` and `###` only, so a contents list can be made of it; its internal anchors are slugged the way GitHub slugs them (diacritics kept — `#nadzorna-ploča`), so the same links work in both renderings; and every ASCII glyph is in backticks (`` `[R]` ``, `` `[=]` ``), which keeps them out of link syntax and renders them monospaced, as they look in the title bars.

What is left to write:

- A page, `src/help/index.html`, built like `customize/index.html`, with a `<!-- manual -->` placeholder — the same shape as `<!-- seo -->` and `<!-- gtag -->`.
- A converter, `src/md.ps1`, dot-sourced by `build.ps1`, which reads `../MANUAL.md` and returns HTML. In memory: writing a generated `.c.html` back into `src/` would put build output in the source tree. `build.ps1` grows by about four lines; the converter is around a hundred.
- The converter handles a fixed subset — `##`/`###` with slug ids, paragraphs, `-` and `1.` lists, `**bold**`, `*italic*`, `` `code` ``, `[text](url)`, and tables — and **throws on anything it does not recognise**, so the manual cannot silently render wrong. The subset is what the document uses; both sides are ours, so that is a contract rather than a shortcut. Implementing CommonMark in PowerShell is not the job.
- Rendering it client-side from the raw `.md` was considered and rejected: it needs a Markdown library or a hand-rolled parser, against the no-dependency grain, and leaves the page empty without JS.

Two things in `build.ps1` the step has to respect:

- **The injection must happen above the path rewrites.** `href="/"` → `/meteo/"` and the rest run before the `<!-- seo -->` replacement, so a manual injected at the usual place would ship its `/customize/` link unrewritten and 404 under `/meteo/`.
- **The comment strip runs after injection** (`(?s)<!--.*?-->`), so the converter must emit no comments. It must also escape `&`, `<` and `>` out of the Markdown's text.
